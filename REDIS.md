# Redis refresh transport

MurmelAPI owns the Redis transport. Paper and Velocity create `redis.properties` in their plugin data directories.
Redis distributes cache invalidations independently of player connections; the database
remains the authoritative source of data.

## Configuration

```properties
enabled=true
host=127.0.0.1
port=6379
username=default
password=YOUR_REDIS_PASSWORD
ssl=false
channel=murmel:production:refresh
server-id=server-1
```

Use the same Redis endpoint, channel and database throughout the network. Each instance
needs a unique `server-id`; a persistent UUID is generated by default. Change it when
copying a plugin directory. Use separate channels for independent networks.

`127.0.0.1` refers to the current host or container. For multiple hosts or containers,
use an address reachable from every instance. Restrict Redis access to the intended hosts.
An empty password skips explicit authentication; otherwise the configured Redis ACL user
and password are used. These are Redis credentials, not operating-system accounts.

Changes take effect after restart. Redis is required: `enabled=false` is rejected;
there is no plugin-message fallback. New configuration files default to `enabled=true`.

## TLS

Set `ssl=true` and use the Redis TLS port. TLS 1.2 and 1.3 are supported. Certificate and
hostname verification are always enabled: `host` must match a DNS name or IP address in
the server certificate's Subject Alternative Name (SAN).

An empty trust configuration uses the JVM's trusted CAs. For a private CA, configure a
PEM CA certificate or bundle. For mutual TLS, also supply the client's certificate chain
and matching PKCS8 private key:

```properties
ssl=true
port=6380
tls.ca-cert=tls/ca.crt
tls.client-cert=tls/client.crt
tls.client-key=tls/client.key
tls.client-key-password=
```

Leave the client certificate/key empty for server-only TLS. Redis must then allow clients
without certificates (`tls-auth-clients no`). Redis ACL authentication is independent of TLS.
For encrypted PEM keys, support depends on the JDK/Netty provider; PKCS12 is a portable
alternative for password-protected client identities.

### PKCS12 or JKS stores

Instead of PEM files, configure Java stores:

```properties
tls.truststore=tls/truststore.p12
tls.truststore-password=YOUR_TRUSTSTORE_PASSWORD
tls.keystore=tls/client.p12
tls.keystore-password=YOUR_KEYSTORE_PASSWORD
tls.store-type=PKCS12
```

`tls.store-type` accepts `PKCS12` or `JKS` and applies to both stores. The private-key
password must match the keystore password. Choose either `tls.ca-cert` or `tls.truststore`,
and either PEM client certificate/key or `tls.keystore`. Custom trust material replaces
the JVM trust roots for this Redis client; global Java SSL settings are unaffected.

All paths can be absolute or relative to the plugin data directory. Use forward slashes
in Windows properties paths. Files must be readable by the service account; restrict
access to private keys and `redis.properties`. Restart after replacing certificates.
Do not distribute the CA's private key to Redis or plugin instances.

### Redis server settings

Example `/etc/redis/redis.conf` for mutual TLS (adjust paths and binding to your deployment):

```conf
bind 127.0.0.1
protected-mode yes
port 0
tls-port 6380
tls-cert-file /etc/redis/tls/server.crt
tls-key-file /etc/redis/tls/server.key
tls-ca-cert-file /etc/redis/tls/ca.crt
tls-auth-clients yes
tls-protocols "TLSv1.2 TLSv1.3"
requirepass YOUR_REDIS_PASSWORD
```

`port 0` disables plaintext connections. Redis needs its server certificate and private key,
and the CA that issued the client certificates. Each client needs its own identity and
trust for the server's CA. Ensure the Redis service account can read its files and restart
Redis after changing its configuration.

## Connection lifecycle

Both platforms publish local refresh events and receive remote events. Remote events are
not republished, and messages from the same `server-id` are ignored. Database/cache work
runs on a dedicated worker rather than Redis IO threads or the Minecraft tick thread.

Initial connection failures retry every five seconds; established connections reconnect
automatically. Subscribing or re-subscribing invalidates the local caches. Failed
publications are combined into a full refresh and retried while the instance is running.
Shutdown drains queued events and attempts to publish any pending refresh before closing
connections. If Redis is unavailable or shutdown times out, delivery is not guaranteed.

Redis Pub/Sub does not store messages or confirm that remote caches applied them. Instances
that miss messages invalidate their caches after reconnecting. This transport is intended
for cache invalidation, not durable event delivery.

References: [Redis TLS](https://redis.io/docs/latest/operate/oss_and_stack/management/security/encryption/),
[Redis ACLs](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/),
[Lettuce client options](https://redis.github.io/lettuce/advanced-usage/client-options/).

## MurmelAPI integration

Start Redis after initializing the database and registering cache listeners:

```java
RedisConfig config = RedisConfig.load(pluginDataDirectory);
murmelAPI.startRedis(config);
```

An overload accepts a `Consumer<RefreshMessage>` for platform notifications. Callbacks run
on the Redis worker; schedule platform work appropriately. Stop application tasks that write
to the database before calling `murmelAPI.stopRedis()`. `murmelAPI.disconnect()` also stops
Redis before closing cache listeners and the database. Only one transport can be started
per MurmelAPI instance. The Lettuce dependency and Redis classes are supplied by MurmelAPI.
